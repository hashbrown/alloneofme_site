# Rendering the Signals feeds

The site currently renders sample entries from `src/data/signal.ts`. Engineering Reads has an Atom subscription URL, and Engineering Leaders has no configured feed URL. Both public Atom feeds returned HTTP 200 on November 22, 2026. The live responses contained 35 Engineering Reads entries and 44 Engineering Leaders entries, and the publisher's health endpoint reported a successful sync for both. Keep the stream names, descriptions, and subscription links in the site, and use the published feeds as the source for entries. [Current stream configuration](../src/data/signal.ts) · [Engineering Reads Atom](https://feeds.alloneof.me/eng.atom) · [Engineering Leaders Atom](https://feeds.alloneof.me/eng-leaders.atom) · [Publisher health](https://feeds.alloneof.me/health)

Astro fetches external data in `.astro` frontmatter, and `@astrojs/rss` generates an outgoing RSS feed. Use a namespace-aware XML parser to read the published Atom `entry` elements. Map their titles, plain-text summaries, and alternate links to the site's existing entry fields. If an RSS source is added later, its `item` elements use `link` and `description` for the corresponding values. ## Static build after feed publication

Fetch and validate the configured feeds during `npm run build`, then deploy `dist/` as Workers Static Assets. Readers receive complete HTML without waiting for the feed origin, and a fully static Astro site can deploy without a Cloudflare adapter. Workers Builds can run the build command and deploy its output with Wrangler. [Astro data fetching](https://docs.astro.build/en/guides/data-fetching/) · [Cloudflare static Astro setup](https://developers.cloudflare.com/workers/framework-guides/web-apps/astro/#if-you-have-a-static-site) · [Workers Builds configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/#how-workers-builds-works)

After a producer sync successfully publishes changed data, check that each changed public feed serves the new revision before posting to a Workers Builds Deploy Hook for the site's production branch. The publisher's one-hour shared cache can still serve stale Atom during revalidation. Keep the hook URL in a secret. Cloudflare returns a `build_uuid` that can be used to verify the build and deployment. Freshness depends on feed availability, build queue time, and deployment. A failed fetch or invalid feed should fail the site build so the previous deployment keeps serving its last successful snapshot. A failed hook or build needs a visible failure and a retry path. [Published Atom response](https://feeds.alloneof.me/eng.atom) · [Workers Builds Deploy Hooks](https://developers.cloudflare.com/workers/ci-cd/builds/deploy-hooks/) · [Workers Static Assets versioning](https://developers.cloudflare.com/workers/static-assets/#how-it-works)

## On-demand Signals route

Configure `@astrojs/cloudflare` manually with Astro's static output default and set `export const prerender = false` on the default Signals page and the stream deep-link page. Workers serves matching static assets directly and runs the Worker for these pages. Check the generated Astro configuration if using `astro add cloudflare`, which Cloudflare's walkthrough describes as selecting `output: 'server'`. [Astro on-demand rendering](https://docs.astro.build/en/guides/on-demand-rendering/#enabling-on-demand-rendering) · [Astro Cloudflare adapter](https://docs.astro.build/en/guides/integrations-guide/cloudflare/#manual-install) · [Cloudflare Astro setup](https://developers.cloudflare.com/workers/framework-guides/web-apps/astro/#if-your-site-uses-on-demand-rendering)

This updates independently of site deployments. On a cache miss, origin latency and failures directly affect the route. Use a parser compatible with the Workers runtime, a fetch timeout, a freshness window, and a fallback for upstream failures. If using the Workers Cache API, its contents are data-center-local and a last-good response needs explicit handling. [Astro Cloudflare adapter runtime](https://docs.astro.build/en/guides/integrations-guide/cloudflare/#cloudflare-module-imports) · [Workers Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/)

## Browser fetch

A static page can fetch and parse feeds in a client-side script. `feeds.alloneof.me` is a different origin from `alloneof.me`. Neither feed returned `Access-Control-Allow-Origin` when checked with `Origin: https://alloneof.me`. A browser implementation would require the feed host to allow the site's origin, or use `*` for public credential-free requests. `no-cors` yields an opaque response whose body the script cannot read. Feed entries arrive after JavaScript and the feed request succeed. Provide loading and error states, and keep subscription links in the initial HTML. [Engineering Reads Atom](https://feeds.alloneof.me/eng.atom) · [Engineering Leaders Atom](https://feeds.alloneof.me/eng-leaders.atom) · [Astro data fetching](https://docs.astro.build/en/guides/data-fetching/) · [Fetch Standard CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol) · [Fetch Standard opaque response](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque)

Use the on-demand routes for Signals. They let the publisher update the feeds on its own schedule and deliver entries in the initial HTML. A static build with a deploy hook is viable if a successful feed publication can trigger and verify a site build. Browser fetching depends on a CORS change and adds a client-side loading state.
